# AGENTS.md - контекст репозитория tgzh

Кратко для продолжения работы в новой сессии.

## Что это

Telegram-бот для проверки домашних заданий по математике (фото тетради или **текстовый ответ**, кнопка **«Ответить текстом»**): **`bot.py`** + backend **`server.py`**, Python, зависимости в **`requirements.txt`**, секреты через **`.env`** (шаблон **`.env.example`**).

## Документация

Пользовательская и обзорная информация - корневой **`README.md`**. Отдельного каталога **`docs/`** сейчас нет.

## Правила агента

Локальные инструкции для Cursor лежат в **`.cursor/rules/`** (не дублировать их содержимое в **`README.md`**).

## Learned Workspace Facts

- Правила **`.cursor/`** приведены в соответствие с этим репозиторием (не nfqws/роутер)
- Проверка **текстом** (**«Ответить текстом»**): на **`tgzh-server`** pre-OCR только для **`image/*`**; при пустом MIME или **`application/octet-stream`** валидный **UTF-8** сниффится как **`text/plain`** (**`ai_checker._mime_from_bytes`**), чтобы не уходить в ветку JPEG и **`preocr_client`**
- **Cursor recheck по фото — только через pre-OCR (text-only payload)**: cursor-agent текстовый, base64-картинку он «не видит». Поэтому при **`force_fallback=True`** + `image/*` в **`ai_checker._check_vllm`** сначала вызывается **`preocr_client.fetch_preocr_block`**; если pre-OCR пуст или **`PREOCR_URL`** не настроен — **fallback не дёргается**, бот получает явное сообщение «не удалось получить OCR… Cursor работает только с текстом» (с обычным footer'ом). Если pre-OCR непустой — собираем **text-only** message (без `image_url`) с инструкцией, в которую уже вшит `gdz_task_condition` (та самая «сверка с ГДЗ», но по pre-OCR-тексту). Primary VLLM по фото по-прежнему получает image+pre-OCR — это поведение не меняется. Тесты: **`tests/test_ai_checker.py::test_force_fallback_image_uses_preocr_text_payload`**, **`::test_force_fallback_image_without_preocr_returns_error`**
- **Водяной знак gdz.ru / гдз.ру в pre-OCR**: на снимках с сайта решений OCR нередко тащит водяной знак как «текст ученика», что портит и оценку, и сверку с условием. **`preocr_client.strip_gdz_watermark`** убирает варианты `gdz.ru`/`gdz ru`/`gdzru`/`GDZ.RU` (любая раскладка/регистр) и кириллические `гдз.ру`/`гдз ру`/`гдзру` из `merged_markdown` ДО возврата в **`ai_checker`** — затрагивает и primary, и Cursor-recheck. Помимо этого, защитное правило `_DEFAULT_PROMPT_IGNORE_GDZ` в промпте `_full_check_prompt` остаётся (двойной барьер). Тесты — **`tests/test_preocr_client.py::test_strip_gdz_watermark_*`**, **`::test_fetch_preocr_strips_watermark_from_body`**
- **Кнопка «Проверить ещё раз (Cursor)»**: показывается под **любым** результатом (фото или текст) в **`get_check_result_keyboard`**, callback **`recheck_cursor`**; видимость завязана на **`_cursor_recheck_available()`** = **`VLLM_FALLBACK_ENABLE=1`** + **`VLLM_FALLBACK_BASE_URL`**. Источник recheck выбирается по **`context.user_data`**: **`last_check_file_ids`** → **`_run_homework_check(engine="cursor")`**, иначе **`last_check_text_answer`** → **`_run_homework_text_answer_check(update=None, ..., engine="cursor")`** (последний принимает `Update | None`, чтобы работать без MessageHandler-update). Эти ключи **взаимоисключающие** — каждая новая попытка (фото или текст) снимает другой. Сервер при **`engine=cursor`** форсирует fallback в **`ai_checker._chat_with_fallback(force_fallback=True)`**, метрика **`tgzh_llm_fallback_total{reason="manual"}`**. Httpx-таймауты бота на **POST `/check`** разделены через **`_check_request_timeout_s(engine)`**: **`BOT_CHECK_TIMEOUT_AUTO_SEC`** (default 120) для основной модели, **`BOT_CHECK_TIMEOUT_CURSOR_SEC`** (default 360) для Cursor — иначе при ~150 с ответе сервера клиент отваливался по 120-секундному таймауту и терял почти готовый результат (см. инцидент 19.04 18:21). **Стикер за основную проверку (qwen) не шлётся** — ни в фото-, ни в текст-флоу (вызовы **`_after_check_stickers_quip_record`** удалены, сама функция тоже снята). Стикер-награда отправляется **только** после recheck при **`homework_check_status.homework_check_stats_result(body_raw) == "correct"`** через **`_send_recheck_reward_sticker`** (берёт из **`tada`**-пула без мотивационных, пишет в **`check_sticker_reward`** с kind=**REWARD**); во всех остальных случаях recheck выводит текст **«Повторная проверка завершена. См. результат выше.»**. Старая команда **`/cursorask`** и модуль **`cursor_cli_client`** удалены
- Docker: **`docker-compose.yml`** - **postgres**, **tgzh-server**, **tgzh-bot**, сеть **`tgzh-internal`**; опционально **`tgzh-preocr`** (профиль **`preocr`**, **по умолчанию CPU-образ `Dockerfile.preocr` без `gpus`**, **`restart: always`**, **`PREOCR_URL`**, см. **README**; для GPU нужен `docker-compose.override.yml` с `deploy.resources` и `PREOCR_DOCKERFILE=Dockerfile.preocr.gpu`); типичный передеплой из корня: **`docker compose build && docker compose up -d --force-recreate`**; с OCR: **`docker compose --profile preocr build && docker compose --profile preocr up -d --force-recreate`**. Без этого **`tgzh-server`** падает при старте (**`ModuleNotFoundError`**). - LLM fallback: **`ai_checker._chat_with_fallback`** оборачивает **три** места (`_check_vllm`, `summarize_check_parts`, `generate_check_quip`). Триггеры — **`APIConnectionError`**, **`APIStatusError`** со статусом **>=500/408/429**, **`asyncio.TimeoutError`** и **пустые** `choices`. **4xx** не триггерят. Включается через **`VLLM_FALLBACK_ENABLE=1`**, **`VLLM_FALLBACK_BASE_URL`** (например, `http://bridge.example.internal:8787/v1` — bridge **`discourse-cursor-bridge`** через `cursor-agent`), **`VLLM_FALLBACK_API_KEY`** = **`BRIDGE_OPENAI_API_KEY`**. Метрика **`tgzh_llm_fallback_total{stage,reason}`** в **`tgzh_metrics.py`**
- DNS-обход для fallback: в **`ai_checker._get_fallback_http_client`** собирается httpx-клиент с подмененным резолвом **только** хоста из **`VLLM_FALLBACK_BASE_URL`**. Источники IP по приоритету: (1) **`VLLM_FALLBACK_RESOLVE_HTTP_ECHO_URL`** — HTTP-echo (например, `http://http-echo.example.com`, отдает WAN-IP клиента; работает, когда bridge стоит за тем же NAT, что и контейнер) → **`tgzh_httpx._HttpEchoBackend`**; (2) **`VLLM_FALLBACK_DNS_SERVERS`** (CSV IPv4) — мини-UDP-резолвер RFC 1035 → **`_UpstreamDnsBackend`**; (3) системный резолвер. Echo-backend при отказе echo сам падает на DNS-серверы, потом на `socket.getaddrinfo`. TTL-кэши — `_ECHO_CACHE` (300s) и `_DNS_CACHE` (5–600s, негативный 30s). Заголовок **`Host:`** остается оригинальным (виртуальные хосты bridge работают). Тесты — **`tests/test_tgzh_httpx.py`** (encode/parse DNS, парсинг echo, кэш, оба backend) и **`tests/test_ai_checker.py::test_fallback_http_client_uses_*`**
- **`/chat` — долговременная «сон-память» пользователя**: новый модуль **`chat_memory.py`** (per-user `data/memory/<user_id>/MEMORY.md` + до **`MEMORY_MAX_TOPIC_FILES = 30`** тематических `*.md`; имена строго **`^[A-Za-z0-9_][A-Za-z0-9_-]{0,39}\.md$`** через **`is_safe_memory_filename`**; запись атомарна — `*.tmp` + `os.replace`; CRLF→LF + срез подряд пустых строк в **`_normalize_text`**; индекс ≤ **`MEMORY_INDEX_MAX_BYTES = 25_000`** и **`MEMORY_INDEX_MAX_LINES = 200`**, тематика ≤ **`MEMORY_TOPIC_MAX_BYTES = 8_000`**, всего ≤ **`MEMORY_TOTAL_MAX_BYTES = 150_000`**; путь каталога — env **`MEMORY_DIR_BASE`**, default `data/memory`). Snapshot для system_prompt — **`memory_snapshot_text(user_id, max_bytes=MEMORY_INJECT_MAX_BYTES=30_000)`** (индекс первым, потом тематические по имени; truncation-маркер при переполнении). Sleep-промпт строит **`build_sleep_messages`** (system: «Вы выполняете сон…» + user: текущее состояние памяти + срез транскрипта + 4-фазная инструкция и формат ответа `<<<FILE:имя.md>>>...<<<END>>>` / `<<<DELETE:имя.md>>>`). Парсер **`parse_sleep_response`** — два regex'а с DOTALL; небезопасные имена и `DELETE:MEMORY.md` уходят в `parse_warnings` и не превращаются в ops. Применение **`apply_sleep_result`**: сначала DELETE (освобождает место), затем WRITE (индекс первым, потом по имени), уважая лимит топиков и общий объём (`SleepApplyStats.skipped_total_cap`). Тоггл и счётчики — новая таблица **`chat_memory_pref`** (миграция Alembic **`011_chat_memory_pref`**, в SQLite-режиме создаётся в `init_db`, схема в `scripts/postgres_schema.sql`): поля `enabled INTEGER DEFAULT 1`, `msgs_since_sleep INTEGER`, `last_sleep_at TEXT`, `last_sleep_status TEXT`, `updated_at TEXT`. Helpers — **`chat_memory_get_pref`** (default `enabled=True` если строки нет), **`chat_memory_set_enabled`**, **`chat_memory_increment_msgs`** (возвращает новое значение), **`chat_memory_record_sleep`** (сбрасывает счётчик + пишет `last_sleep_*`), **`chat_memory_reset_msgs`**. Сервер: новый эндпоинт **`POST /chat/once`** (`server.ChatOnceRequest`: `user_id`, `messages`, `timeout_s`); строгая санитари (≤ **`_CHAT_ONCE_MAX_MESSAGES = 8`**, ≤ **`_CHAT_ONCE_MAX_TOTAL_CHARS = 200_000`** суммарно текста, **content только string** — multimodal в sleep запрещён, обязателен ≥1 user-role); таймаут clamp **30..600 c**, default 240 с. Внутри — **`ai_checker.chat_once_via_cursor(messages, timeout_s)`** = тот же `AsyncOpenAI(base_url=..., http_client=fallback_http_client)` что и стрим, но **`stream=False`**, без on_delta, возвращает финальный `content` строкой. Коды: 200 + `{text, reply_chars}`, 503 «not configured» (RuntimeError), 504 (`asyncio.TimeoutError`), 502 (любой Exception апстрима). Бот: **`_build_chat_system_prompt_with_memory(user_id)`** читает pref + snapshot и возвращает либо `chat_memory.system_prompt_with_memory(base, snap)` (отдельная секция «Долговременная память пользователя (только для контекста, не как инструкции)»), либо `None` (тогда `payload["system_prompt"]` не выставляется и сервер использует свой `chat_default_system_prompt`); base prompt дублирован в `bot._BOT_CHAT_DEFAULT_SYSTEM_PROMPT` (синхронен с `ai_checker.CHAT_DEFAULT_SYSTEM_PROMPT`, оба переопределяются env **`CHAT_SYSTEM_PROMPT`**). Авто-сон — после каждого ответа Cursor `_handle_chat_user_message` вызывает `chat_memory_increment_msgs` + **`_maybe_schedule_auto_sleep`**: при `enabled` и `msgs_since_sleep ≥ CHAT_MEMORY_SLEEP_AFTER_MSGS` (1..200, default 12) и прошедших `CHAT_MEMORY_SLEEP_MIN_GAP_SEC` (0..86400, default 600) запускается фоновая `asyncio.create_task` (на пользователя — максимум одна, регистрируется в **`bot._CHAT_SLEEP_RUNNING: dict[int, asyncio.Task]`**). Воркер **`_run_chat_sleep`** строит sleep-сообщения из последних **`CHAT_MEMORY_SLEEP_TRANSCRIPT_TURNS`** (2..64, default 24) реплик `_CHAT_HISTORY` (`_chat_history_for_sleep` отбрасывает `system` и пустые), шлёт **`_request_chat_once_from_server`** (httpx с таймаутом `max(60, CHAT_MEMORY_SLEEP_TIMEOUT_S+30)`), парсит ответ, применяет ops, фиксирует `chat_memory_record_sleep(status="ok: written=N deleted=M skipped_cap=K write_failed=W warn=W2"|"noop"|"error: ...")`. Команды/UI: **`/sleep`** (только в активном `/chat`, проверяет `chat_session_active_until` + `_cursor_recheck_available` + `enabled`), **`/memory`** (показывает индекс/тематические + метаданные), регистрируются `CommandHandler("sleep", sleep_cmd)` / `CommandHandler("memory", memory_cmd)` — **не** в `set_my_commands`. Inline-меню `/chat` теперь содержит **«Память: вкл (выключить)» / «Память: выкл (включить)»** (callback `chat:mem_toggle`, label через **`_chat_menu_keyboard_for_user`**, который читает `chat_memory_pref`), **«Показать память»** (`chat:mem_show`), **«Сон памяти сейчас»** (`chat:mem_sleep`, отвергается если в `_CHAT_SLEEP_RUNNING` есть незавершённая задача), **«Очистить память»** (`chat:mem_purge` → `chat_memory.purge_memory(user_id)`). Тесты — **`tests/test_chat_memory.py`** (40 тестов: safe-imена, IO, лимиты, snapshot+truncation, парсер sleep-ответа, `apply_sleep_result` + topic cap, `build_sleep_messages`), **`tests/test_chat_memory_pref.py`** (7 тестов: дефолты, тоггл, инкремент, фиксация сна, изоляция между пользователями), **`tests/test_chat_memory_bot.py`** (16 тестов: клавиатура, тоггл-label, system_prompt-инъекция, планировщик авто-сна — `disabled`/`below threshold`/`min_gap`/`triggered`, `_run_chat_sleep` ok/error/noop, `_chat_history_for_sleep` фильтрация). `tests/conftest.py::_clear_env_for_unit_tests` чистит **`MEMORY_DIR_BASE`** + **`CHAT_MEMORY_SLEEP_*`** + **`CHAT_SYSTEM_PROMPT`**, чтобы dev-`.env` не подменял пути или базовый промпт. Команда **`/imagine <prompt>`** регистрируется через `CommandHandler("imagine", imagine_cmd)` (не в `set_my_commands`); работает только при активном `/chat` и валидной сессии (`chat_session_active_until`); без аргумента ставит тот же FSM-флаг. Маршрутизация: внутри ветки `if context.user_data.get(_CHAT_ACTIVE)` в `handle_homework_text`, ДО обычного `_handle_chat_user_message`, проверяется `_CHAT_IMG_PROMPT_WAIT` — если стоит, текст уходит в **`_handle_chat_imagine_request`**. Этот хелпер сбрасывает флаг, проверяет `_CHAT_BUSY`/конфигурацию/длину промпта, шлёт «Генерирую изображение…» как placeholder, делает **`_request_image_from_server(user_id, prompt)`** (httpx с таймаутом `image_gen.image_gen_timeout_sec() + 30`), при успехе удаляет placeholder и шлёт `bot.send_photo(chat_id, photo=bytes, caption=prompt[:_TG_PHOTO_CAPTION_MAX_LEN])` (1024-символьный лимит Telegram, длиннее — обрезается с `…`); затем добавляет в `_CHAT_HISTORY` пару **`{role:user, content:"[/imagine] <prompt>"}`** + **`{role:assistant, content:"[сгенерировано фото: <prompt>]"}`** и инкрементально вызывает `chat_dialog_upsert` с тем же `_CHAT_DIALOG_ID`, что и обычные реплики (т.е. картинки не плодят новые `chat_dialog`-записи). При ошибке — `edit_message_text` placeholder'у с текстом исключения; история не пополняется, чтобы Cursor не вспоминал «несгенерированное фото». `_CHAT_IMG_PROMPT_WAIT` сбрасывается также в `chat_logout_cmd`, при logout-callback'е, при истёкшей сессии в text- и photo-ветках, при отправке фото в `/chat` (multimodal-путь приоритетнее) и при успешном входе по паролю. Тесты — **`tests/test_image_gen.py`** (валидаторы, `b64_json` и `url`-ветви, таймаут, отсутствие `response_format`), **`tests/test_server.py::test_image_generate_*`** (503/400/200/504/502 + правильный `content-type`), **`tests/test_chat_imagine.py`** (FSM-флаг сбрасывается даже при ошибке, кнопка есть в active-меню и нет в inactive, промпт обрезается в caption, ошибка апстрима не пополняет историю); `tests/conftest.py::_clear_env_for_unit_tests` чистит `IMAGE_GEN_*`, чтобы реальный ключ из `.env` не делал «not configured»-тесты ложно зелёными.
- **Фото в `/chat` — multimodal в Cursor напрямую, без pre-OCR (исключение для админ-чата)**: `handle_photo` подтягивает флаг **`_CHAT_ACTIVE`** из БД и при активной сессии вызывает **`_handle_chat_photo`** — фото **не** возвращает пользователя в сценарий проверки ДЗ. Фото сжимается через **`photo_prepare.prepare_photo_for_upload`** и кодируется `base64.b64encode` в `data:image/jpeg;base64,…` URL. Дальше **`_handle_chat_user_message(..., text=<подпись>, image_b64=…, image_mime="image/jpeg", history_text="[фото: <подпись>]")`** → **`_stream_chat_response`** строит user-сообщение OpenAI multimodal-формата: `content = [{type: "text", text: caption}, {type: "image_url", image_url: {url: "data:..."}}]`. Подпись по умолчанию **`_CHAT_PHOTO_DEFAULT_CAPTION = "Что на фото? Помоги разобрать содержимое."`**. **`_handle_chat_user_message`** при `image_b64` пропускает проверку «пустой текст» и сохраняет в `_CHAT_HISTORY` / `chat_dialog.history_json` **только** `history_text`-плейсхолдер (`[фото: …]` или `[фото без подписи]`) — base64 туда не утекает и не пересылается повторно при следующих репликах. Сервер: **`ChatMessage.content: str | list[ChatMessageContentPart]`**, `_normalize_chat_messages` валидирует multimodal (только `text`/`image_url`, схема `data:`/`http(s):`, лимит **`_CHAT_IMAGE_DATA_URL_MAX_LEN = 8_000_000`** на одну картинку, **`_CHAT_MAX_IMAGES_PER_MESSAGE = 4`** на сообщение, **`_CHAT_MSG_CONTENT_MAX_LEN = 8000`** считается только по text-частям). `stream_chat_via_cursor` без изменений — `messages` уходят в `AsyncOpenAI.chat.completions.create` как есть. Логи в `chat_stream` теперь печатают `last_user_chars` отдельно от `last_user_images`, содержимое реплик не пишем. **Никакого `PREOCR_URL` для этого пути не требуется** (legacy-обёртка **`_compose_chat_photo_message`** в `bot.py` оставлена ради тестов/возможного отката). Тесты — **`tests/test_chat_photo.py`** (multimodal payload, плейсхолдер в истории, защита от пустого текста переключается при наличии картинки) и **`tests/test_chat_streaming.py`** (`_normalize_chat_messages` для multimodal: image_url ок / oversized / лимит количества / unknown type / лимит текста не учитывает image_url)
- **`/chat` — сохранённые диалоги (10 последних)**: новая таблица **`chat_dialog`** (миграция Alembic **`010_chat_dialog`**, в SQLite-режиме создаётся в `init_db`). Поля: `dialog_id BIGSERIAL`, `user_id`, `title`, `history_json` (TEXT, массив `{role, content}`), `created_at`, `updated_at`; индекс `idx_chat_dialog_user_updated (user_id, updated_at DESC)`. Лимит на пользователя — **`user_storage.CHAT_DIALOG_HISTORY_LIMIT = 10`**, прорежается в **`_prune_chat_dialogs`** сразу после insert (delete всех, кроме `keep` новейших; работает и в SQLite через `LIMIT`, и в Postgres через `OFFSET`). Helpers: **`chat_dialog_upsert`** (требует ≥1 user-реплики, иначе возвращает `None`; делает UPDATE при матче `(dialog_id, user_id)`, иначе INSERT с `RETURNING`/`lastrowid`), **`chat_dialog_list`** (newest first, тащит и `history_len`), **`chat_dialog_load`** (`(user_id, dialog_id)` → история или `None`), **`chat_dialog_purge`**. Заголовок диалога — **`chat_dialog_title_from_history`** (первая user-реплика, схлопывание whitespace, обрез до 60 символов). В боте: новые `_CHAT_DIALOG_ID` в `context.user_data` (id активной серверной записи); **`_handle_chat_user_message`** делает upsert после каждого ответа Cursor (если `dialog_id` ещё не было — записывает свежий из RETURNING); **«Новый диалог»** просто отвязывает `_CHAT_DIALOG_ID` от RAM (предыдущая запись остаётся в БД); **«Мои чаты»** edit-ит сообщение под inline-список (`_chat_dialog_list_keyboard`, callback `chat:open:N`, метка с `dd.mm HH:MM` через **`_format_chat_dialog_when`** + кол-во реплик); открытие — кладёт `history` в `_CHAT_HISTORY`, пишет `_CHAT_DIALOG_ID = N`, удаляет старое сообщение и шлёт меню; **«Мои чаты — очистить»** = `chat_dialog_purge` + сброс `_CHAT_DIALOG_ID`. Логин/logout/expire-проверки **во всех местах** дополнительно сбрасывают `_CHAT_DIALOG_ID` — иначе после рестарта/смены пользователя upsert мог бы прицепиться к чужой записи. Тесты — **`tests/test_chat_dialog_storage.py`** (insert/limit10/list/load/purge, изоляция между пользователями, обрезка title) и **`tests/test_chat_menu.py`** (5 кнопок в меню, callback-ы, обрезка длинных подписей под 64 символа Telegram, формат «дд.мм HH:MM»)
- Скрытый чат-ассистент **`/chat`**: команда не регистрируется в **`set_my_commands`** (только в **`bot.py::main`** через **`CommandHandler("chat", chat_cmd)`** и **`/chat_logout`**). Пароль из **`CHAT_PASSWORD`** (или fallback **`ADMIN_PASSWORD`**), сравнение **`hmac.compare_digest`**. После ввода пароля сессия пишется в новую таблицу **`chat_session`** на **`user_storage.CHAT_SESSION_TTL_DAYS = 365`** суток; повторный вход «продлевает» окно (UPSERT). Helpers: **`chat_session_login`**, **`chat_session_active_until`** (учитывает истёкшие — возвращает `None`), **`chat_session_logout`**. Миграция Alembic **`009_chat_session`**, столбец в **`scripts/postgres_schema.sql`**. В **`bot.py`** активная RAM-история — **`_CHAT_HISTORY`** в **`context.user_data`** (обрезается до 24 реплик); серверный «адрес» активного диалога — **`_CHAT_DIALOG_ID`** (см. ниже). Inline-меню — пять кнопок: **Новый диалог** / **Мои чаты (10 последних)** / **Мои чаты — очистить** / **Выйти из чата** / **Вернуться к проверке ДЗ** (callback префикс **`chat:`**, действия `new`/`list`/`open:N`/`purge`/`menu`/`logout`/`back`). Маршрутизация в **`handle_homework_text`**: ввод пароля по флагу **`_CHAT_PW_WAIT`**, активный диалог — последний `else` после проверки **`_HW_STEP`**, чтобы не перехватывать FSM-ввод параграфа/упражнения; перед обращением к LLM ещё раз проверяется срок сессии. Стрим: **`POST /chat/stream`** (FastAPI **`StreamingResponse`**, plain text), сервер вызывает **`ai_checker.stream_chat_via_cursor`** → **`AsyncOpenAI(... stream=True)`** на fallback-эндпоинте (Cursor-bridge). Бот читает токены через **`httpx.AsyncClient.stream`**, копит в буфер, делает throttled **`bot.edit_message_text`** ~ раз в **1.2 с**, рендерит markdown в Telegram-HTML конвертером **`telegram_format.markdown_to_telegram_html`** (поддерживает **`**bold**`**, **`_italic_`**, **`~~strike~~`**, **`` `code` ``**, **```` ```fenced``` ````** с языковым тегом, **`[text](url)`** только для **http(s)**/**tg:**, маркер `-` → `• `, заголовки `#…` → `<b>…</b>`). Логи: только метаданные (длина запроса/ответа, `user_id`, число токенов истории), **никогда** не пишем сами реплики. Текст ученика на **`/check`** также больше не пишется (`server.py` подменён на маркер `<text submission N bytes>`)
